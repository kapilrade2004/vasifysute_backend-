# 1. Platform Overview & Core Principles

Vasify SUITE is a **modular business management SaaS platform** where organizations can select the services they need and operate them from one unified workspace.

### Core Principles
The platform natively supports:
- Multiple organizations with strict isolation.
- Multiple users per organization with granular role permissions.
- Pluggable business services (CRM, Finance, HR, Projects, Workspace, and more).
- Service-based subscriptions and automated activation/deactivation.
- Organization-specific customizations (custom fields, pipelines, layouts, workflows, branding).
- Cross-service consolidated reporting and analytics.
- Centralized multi-channel notifications (In-app, Email, WhatsApp, Push).
- Centralized document repository and digital asset vault.
- Complete chronological audit trails and activity timelines.
- Drag-and-drop business automations and approval hierarchies.
- External client portals and internal employee self-service portals.
- Comprehensive Master Platform Administration.

## 4. 👤 User Management & Two-Tiered RBAC

Vasify strictly separates **Platform Administrators** from **Tenant Business Users**:

### 1. Platform Users (Internal Vasify Staff)
- `SuperAdmin`: Full system control, billing, tenant lifecycle, and DB diagnostics.
- `SupportAdmin`: Tenant support tickets, read-only audit inspection, user assists.
- `FinanceAdmin`: Platform billing oversight, subscription reconciliation.

### 2. Tenant Users (Customer Organization Staff)
- `OrgOwner`: Full organization ownership, subscription billing, module activation.
- `OrgAdmin`: Department-wide configuration, custom fields, user invitations.
- `Manager`: Team lead approvals, pipeline management, leave approvals.
- `Employee`: Personal tasks, timesheets, assigned leads, personal attendance.
- `Viewer`: Read-only access to authorized modules.

### Dynamic Permission Nodes


# 16. Vasify Suite — Phased Scope of Work (UI/UX Focus)

This scope is organized into build phases. Each phase lists **what screens/flows exist**, **what states each screen needs**, and **which interaction pattern to use** (inline edit vs. drawer vs. modal vs. full page) — based on your existing SOW/architecture and current SaaS UX practice. No implementation/build instructions are included, as requested.

---

## Phase 0 — Design System Foundation (do this before any screen work)

This is the single highest-leverage phase. Every module below inherits from it, so inconsistency here multiplies across 40+ modules.

- **Design tokens**: color scale (brand + semantic: success/warning/danger/info), spacing scale, typography scale, radius, shadow/elevation levels.
- **Density mode**: Vasify is a data-heavy operational tool (like Linear/NetSuite), not a marketing app — decide your baseline information density now (compact tables, tight row height) rather than defaulting to airy minimalism you'll have to walk back later.
- **Core interaction primitives** (define once, reuse everywhere):
  - **Inline click-to-edit field**: text turns into input on click, autosaves on blur/Enter, Esc reverts, subtle pencil affordance on hover. This is your default for single-field edits — you've already got this right per current best practice.
  - **Drawer/side panel**: for editing a full record while keeping list context visible (e.g., editing a Lead from the pipeline board without losing the board).
  - **Modal**: reserved only for short, must-finish-or-cancel tasks — confirmations, destructive actions, quick single-purpose creates. Not for multi-field record editing.
  - **Full page**: for multi-step or heavy-context edits (e.g., Payroll run, Invoice builder with line items).
- **Table component**: sticky header, column resize/reorder/hide, row density toggle, inline edit per cell, bulk-select checkbox column, empty/loading/error states.
- **Status/tag chip system**: consistent color-coding rules across CRM stages, invoice statuses, ticket priorities, etc. (don't let each module invent its own palette).
- **Empty states, loading skeletons, error states** — designed once as reusable patterns, not per-screen.
- **Notification/toast system** for save confirmations (since inline edit removes the modal's built-in "saved" feedback — you need a lightweight substitute, e.g. a brief checkmark flash or toast).
- **Role-based visibility rules**: how a component visually differs (or hides) based on OrgOwner / OrgAdmin / Manager / Employee / Viewer.

2. White-label branding settings (logo, colors, domain, email signature, PDF templates)
3. Mobile-responsive pass across: Lead creation, Clock In/Out, Task updates, Approvals (your SOW already flags these four as mobile priorities)

**UX notes:**
- **Marketplace**: card grid per module, each showing status (Not Active / Trial / Active), with contextual CTA button that changes per state — don't reuse one generic "Learn More" button across all states.
- **White-label**: live preview pane showing how the branding changes will look on an actual invoice PDF / portal login screen, not just color swatches in isolation.
- **Mobile pass**: don't treat this as "make everything responsive" — explicitly scope which flows get first-class mobile design (per your own priority list) vs. which get basic responsive fallback only.

## Suggested Sequencing Logic

If you want a build order rather than just a module list, the dependency chain looks like this:

```
Phase 0 (Design System)
   ↓
Phase 1 (Auth/Onboarding) → Phase 2 (Shell/Dashboard/Nav)
   ↓
Phase 3–6 (CRM → Finance → HR → Projects, in whatever order matches your sales priority)
   ↓
Phase 7 (secondary modules, can be deprioritized/parallelized)
   ↓
Phase 8 (Customization Engine) — needs at least CRM+Finance built first, since it customizes those entities
   ↓
Phase 9 (Reports/Import-Export) — needs real modules with real data to report on
   ↓
Phase 10 (Portals) — needs Finance+Projects+HR data to expose externally
   ↓
Phase 11 (Settings/Billing/Admin) — can actually start early in parallel, since Platform Admin doesn't depend on tenant modules being finished
   ↓
Phase 12 (Marketplace/White-label/Mobile polish) — last, since it's cross-cutting polish over everything above
```
